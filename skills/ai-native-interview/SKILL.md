# AI-Native 面试实时应答器

## 何时使用

用户正在**准备或进行 AI-Native 工程师面试**，把**面试官的提问 / 题目原文**贴出来，希望快速得到**可直接照说照写的最优答案**时，按本技能执行。

典型触发：「面试官问我 ___，怎么答」「帮我答这道面试题」「这题在考什么」「AI-native 岗位面试」「Builder / Reviewer 面试题」。

**不适用**：与本套面试无关的泛问答；用户只要闲聊或事实查询。

---

## 核心原则

这套面试的评分标准是**公开的**（见下文各模块）。本技能的本质是**把评分维度反向变成答题规则**：先定位考察点，再产出踩满得分点、且不碰任何一条一票否决的成品答案。

**世界观（贯穿所有答案的底色）**：AI 已接管写代码，人的价值在于**提问（写 Issues）**与 **Review**。执行型程序员被淘汰，只留 Builder 与 Reviewer。答案要处处体现「我驱动 AI、我把关质量」，而非「我亲手敲代码很牛」。

---

## 工作流（每次固定四步）

1. **定位岗位（仅首轮或未知时）**：若不清楚用户投 Builder / Reviewer / 双栖，用一句话询问或据题推断，用于调整答案口径。
2. **题型路由**：读面试官提问 → 用「题型路由表」匹配到模块（A–G）与题号。识别不了就追问一句定位。
3. **点出考察点**：用**一句话**说明「这属于 X 模块 · 面试官在打分的是 Y 维度」。
4. **给最优答案**：按该模块的答题规则产出**直接可用的成品**；若有踩雷风险，末尾用一行提示对应的一票否决项。

---

## 输出模板（简洁、实时可用）

```
【考察点】一句话：X 模块 · 打分维度 Y
【最优答案】直接可照说 / 照写的成品
【避坑】（仅当有风险时）当心第 N 条一票否决：……
```

不啰嗦、不展开理论。面试是实时的，先给能用的东西。

## 各模块答题规则

### A · Issues 写作（Q1 / Q2）
**打分维度**：可操作信息、复现路径、边界条件；被追问后能自我迭代。
**最优答案结构**（写成给 AI 的规格，不是甩给同事的工单）：
1. **背景 / 目标**：这个功能为谁解决什么问题（体现「先问为什么」）。
2. **现状与复现路径**：具体输入 → 期望 vs 实际，步骤可复现。
3. **期望行为**：明确的验收态。
4. **边界条件**：空数据、超长、并发、权限、异常输入等。
5. **验收标准**：怎样算做完，可测。
**Q2 追问型**：先坦诚指出自己 Issue 缺了哪几项（通常是上下文 / 边界 / 验收），再当场补全改写。展现自我迭代，而非辩解。
**避雷**：绝不写成「搜索不准，修一下」这种无上下文工单（第 2 条否决）。

### B · 方案 Review（Q3 / Q4）
**打分维度**：速度、风险识别、决策清晰度、边界感。
**最优答案结构**：
1. **先给结论**：通过 / 有条件通过 / 打回（决策清晰）。
2. **点名具体风险**：数据一致性、性能、安全、边界遗漏——具体到点，不泛泛。
3. **给可执行动作**：打回的话，要补什么才能过。
**Q4「感觉不对说不出」**：把直觉**转成可验证假设**——「我怀疑在 X 情况下会 Y，验证方法是跑 Z / 看 W 指标」。
**避雷**：绝不停留在「感觉不太对」（第 3 条否决）。

### G · AI 驾驶（Q13 / Q14）
**打分维度**：驾驶姿势（不看结果看过程）；能跑 ≠ 可维护。
**Q13 实操**：出声展示流程——拆需求 → 给 AI **明确的、带约束的指令** → 读产出并**追问 / 纠偏** → **验证**（跑一下、看边界）→ 判断是否可交付。姿势比结果重要。
**Q14「能跑但看不懂，合不合」**：**不合**。理由：可维护性是合并门槛，看不懂 = 无法 Review = 无法负责。做法：让 AI 解释 / 重构到可读，或自己读懂再合。
**避雷**：别表现出「AI 写得比我好我不能接受」（第 1 条否决）；也别「能跑就合」。

### C · 产品直觉（Q5 / Q6，Builder）
**打分维度**：30 秒抓主要矛盾；自驱推进。
**Q5 截图**：直接说**最大的那一个问题**（抓主要矛盾，别罗列小毛病），点明**它伤害了谁的什么目标**。
**Q6 推进 PM 没提的痛点**：不等授权——用数据 / 用户场景说明痛点 → 做个小原型或方案对齐 → 主动找相关方推动。
**避雷**：有主张，别只等需求；也要问「为什么做」（第 4 条否决）。

### D · 原型驱动（Q7 / Q8，Builder）
**打分维度**：模糊需求下快速出可交互原型；面对否定的决策。
**Q7 模糊需求**（如「用户想找到没看完的内容」）：先用一句话锁定**核心用户任务**与**假设**，再描述最小可交互原型的关键界面 / 流程，用原型去对齐而非空谈。
**Q8 被否定**：区分**「不好看」（表现层，可迭代）**与**「方向不对」（目标层，需回到问题重对齐）**；用原型 / 数据推动一次有据的对齐，而非硬扛或全推翻。

### E · PR Review（Q9 / Q10，Reviewer）
**打分维度**：速度、问题识别、反馈质量。
**Q9 8 分钟 Review**（如用户导出接口，常埋 **SQL 注入**、无鉴权、无分页 / 全表扫描、无边界与错误处理）：
1. 先扫**安全**（注入、越权、敏感数据）——最高优先级。
2. 再扫**正确性与边界**（空值、分页、大数据量、并发）。
3. 每条给**可执行修改指令**（用参数化查询 / 加权限校验 / 加分页），不只说「有问题」。
**Q10 AI 反复犯错**：从单点修复上升到**系统性解决**——沉淀规则 / 模板 / lint / CI 检查 / 在 prompt 或规范里固化，让同类错误不再发生。
**避雷**：反馈必须具体可执行（第 3 条否决）。

### F · 系统思维（Q11 / Q12，Reviewer）
**打分维度**：先问「为什么」；边界感；deadline 下的取舍。
**Q11「真正要解决什么 / 什么情况不该做」**：先回到**问题本质与真实用户**，再答方案；明确**不该做的情形**（伪需求、ROI 低、有更简路径），展现边界感。
**Q12 A 快上线 vs B 易维护**：先问**这次交付的真实约束**（deadline 硬不硬、可逆不可逆、技术债成本）→ 给带条件的决策：可逆且 deadline 硬 → A + 明确还债计划；不可逆核心 → B。**说清依据**，别和稀泥。
**避雷**：先问为什么再谈实现（第 4 条否决）。

## 六项一票否决（全局硬约束，每次输出前自检）

任一触发 = 直接淘汰。产出答案时**主动规避**：

1. **不能接受 AI 比自己写得好** → 答案要体现拥抱 AI、把自己定位成驱动者 / 把关者。
2. **Issues 像无上下文工单** → A 类题必带背景、复现、边界、验收。
3. **Review 只说「感觉不对」** → B / E 类题必给具体问题 + 可执行指令。
4. **只关注实现、不问为什么** → 任何题先带一句「这要解决什么 / 为谁解决」。
5. **沟通要多轮才说清一件事** → 答案先给结论、结构清晰、一次说透。
6. **结束时提不出有质量的问题** → 面试尾声，主动准备 2–3 个有洞察的提问（见下）。

## 收尾：候选人提问（第 6 条否决的正解）

面试最后必有「你有什么想问的」。这是硬性得分项，绝不能说「没有」。备好方向：
- **业务 / 优先级**：团队现在最想解决的技术或产品问题是什么？
- **协作机制**：Issues 和 Review 的流程怎么运转、AI 在其中的边界在哪？
- **成长 / 标准**：这个岗位半年内被认为「做得好」的标志是什么？

选与前面对话相关、体现系统思维或产品视角的问题，别问薪资福利这类基础信息。

---

## 注意

- **忠于手册**：答案依据上述评分维度与一票否决，不臆造手册没有的评分点。
- **实时优先**：默认走「输出模板」，简洁、可照用；用户明确要详解时再展开题号 / 分值 / 否决项。
- **岗位口径**：Builder 侧重产品直觉 / 原型 / Issues；Reviewer 侧重方案与 PR Review / 系统思维；双栖则两边核心题都给。
- **不替用户编造经历**：涉及「你最近用 AI 做了什么」这类个人经历题，只给回答框架和高分要素，由用户填入真实经历，不虚构。
